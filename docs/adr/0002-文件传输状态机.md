# 文件传输状态机（单槽 + 轮询分片 + 公告驱动）

**Status**: accepted

M4 文件传输的实现架构，围绕服务器（TCPServer）已实现的 MSG_FILE_* 帧族设计客户端侧状态机，四个决策点：

1. **轮询分片发送**：发送方收到 accept 后不阻塞事件循环，主循环每轮发送 ≤4 个分片（约 256KB，等于服务器写缓冲上限），发送期间 poll 超时从 200ms 降为 50ms，期间聊天收发不中断。对照：阻塞式一次发完全部（代码最少、无状态机，但大文件发送期间界面冻结，且更暴露服务器写缓冲 256KB 静默丢包风险）。选择轮询分片，是 ADR-0001 预警的"M4 大文件传输阻塞事件循环"的对策——**有界批量阻塞**而非整文件阻塞。

2. **单槽限并发**：发送全局单槽（槽忙时新 /sendfile 本地拒绝）；接收最多 8 个 pending + 至多 1 个活动接收（第二个 /accept 本地拒绝，pending 满时对新公告自动回发 REJECT）。对照：服务器允许任意多并发传输。选择单槽：单线程事件循环 + 单进度显示 + 单 FILE* 写路径下，多活动传输需按 tid 轮换批量与多条进度行，复杂度不成比例；学习项目语义清晰优先，覆盖全部协议教学点。

3. **公告驱动 tid 解析**：tid 由服务器分配、只存在于公告文本（INIT 帧载荷无 tid，协议事实），客户端解析 "[Server] File transfer #N ..." / "Incoming file transfer #N ..." 获取；**公告是主驱动信号，控制帧是冗余信号**（幂等双信号处理，防单一路径丢失）。服务器固定"公告先入队、帧后入队"，且断线取消只有文本公告无 CANCEL 帧——必须双信号。

4. **落盘安全**：接收文件存客户端运行目录下 downloads/，文件名 basename 化（防目录穿越——服务器不校验文件名，`../evil` 是合法输入）再唯一化（同名加序号，不覆盖）。

**Consequences**:
- 每轮批量 ≤256KB 结构性规避服务器写缓冲静默丢包（前提：接收方每轮至少能排空一部分，轮询节奏下成立）
- 服务器无 chunk 确认/重传、无超时清理（怪癖，服务器侧议题）：客户端接收侧以 offset 连续性 + 字节数校验兜底，不连续/不完整 → 主动取消并删除半成品；发送侧无回执，完成判定依赖 complete 公告
- 断线取消只有文本公告：客户端公告与帧双信号处理，公告解析失败（服务器未来改文案）则无法关联 tid，记为已知限制
- protocol.c 新增 protocol_build_text3 / protocol_build_tid / protocol_build_chunk 三个组帧函数（客户端超集，镜像服务器 payload_append_field 语义），与服务器 protocol.c 不再逐字节一致——提交说明须注明有意偏离
