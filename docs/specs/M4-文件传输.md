# M4 文件传输

## Problem Statement

服务器（TCPServer）已完整实现文件传输（file_transfer.c：MSG_FILE_INIT/ACCEPT/REJECT/CHUNK/COMPLETE/CANCEL 帧族、传输状态机、tid 分配与中转），客户端却完全没有使用它——四命令缺失、全部 MSG_FILE_* 帧落分发默认分支（仅提示"M4 扩展"）。文件传输不可用。服务器侧存在多个需要客户端适配的约束：tid 只存在于公告文本、无 chunk 确认、写缓冲 256KB 超限静默丢包、断线取消只发文本公告。

## Solution

新增 file 模块承载传输状态机，新增 4 个命令：`/sendfile <目标> <文件>`、`/accept <tid>`、`/reject <tid>`、`/cancel <tid>`；app 模块分发新增 MSG_FILE_* 六个 case 与公告挂钩。发送侧采用**轮询分片**（每轮 ≤4 片 ≈ 256KB，不阻塞事件循环，发送期间可继续聊天）；接收侧落盘 downloads/（basename 化 + 同名加序号）。tid 从公告文本解析（协议强制），公告为主驱动信号、控制帧为冗余信号。状态机架构决策见 ADR-0002。

## User Stories

1. 作为已登录用户，我想用 `/sendfile <目标> <文件>` 发送本地文件，以便把文件传给在线好友
2. 作为发送方，我想在提交后立即收到中文确认提示与服务器等待公告（`File transfer #N: 'name' (N bytes) → bob. Waiting for acceptance...`），以便确认传输已建立并得知传输标识
3. 作为发送方，我想在目标不在线时收到 `错误(200): Target user not found` 且任务被清理，以便立即知道发送失败（不做离线排队）
4. 作为发送方，我想在提交空文件或打不开的文件时被本地拒绝，以便不发出无意义的传输
5. 作为发送方，我想在目标 accept 后自动开始分片发送，以便无需手动操作
6. 作为发送方，我想在发送期间继续收发聊天消息（界面不冻结），以便保持聊天体验
7. 作为发送方，我想看到发送进度（每 1MiB 一行 `发送中 #N: 已发/总字节 (百分比)`），以便了解传输进展
8. 作为发送方，我想在全部字节发完后自动发送完成帧并看到 complete 公告（`File transfer #N complete: 'name' (M/N bytes transferred).`），以便确认传输成功
9. 作为发送方，我想在对方 reject / cancel / 断线时任务被清理、槽位释放，以便可以发起新的发送
10. 作为接收方，我想看到 incoming 公告（`Incoming file transfer #N from alice: 'name' (N bytes). Accept or reject?`），以便决定是否接收
11. 作为接收方，我想用 `/accept <tid>` 接受文件并自动落盘到 downloads/，以便拿到文件
12. 作为接收方，我想用 `/reject <tid>` 拒绝文件，以便不接收不想要的文件
13. 作为传输任一方，我想用 `/cancel <tid>` 主动取消传输，以便中止错误或不再需要的传输
14. 作为接收方，我想收到的文件与源文件字节一致（校验通过才保留），以便拿到完整可靠的文件
15. 作为接收方，我想在收到重复/越界 offset 的分片或最终字节数不符时收到提示且半成品被删除，以便不留下损坏文件（服务器多线程转发可能乱序到达，客户端按 offset 定位写盘、乱序不视为错误）
16. 作为接收方，我想在同名文件已存在时自动加序号（`name`、`name (1)`...），以便不覆盖已有文件
17. 作为用户，我想在发送槽忙或已有活动接收时收到本地拒绝提示，以便知道命令为何被拒
18. 作为用户，我想在 /accept /reject /cancel 使用非数字或越界 tid 时看到用法提示，以便不发出无效请求
19. 作为用户，我想在 `/help` 中看到文件传输命令说明，以便发现该能力
20. 作为用户，我想在多个 incoming 传输待处理时逐个决定（accept 一个、reject 其余），以便分别处理
21. 作为聊天用户，我想文件传输的进度与提示与聊天消息同样不打断输入行地显示，以便保持一致的阅读体验
22. 作为发送方，我想发送期间对方断线时任务被清理（收到 `File transfer #N cancelled: bob disconnected.` 公告），以便及时了解传输失败

## Implementation Decisions

- **模块**：新增 file 模块（传输状态机：发送/接收任务槽、文件句柄、进度水位——模块级状态，命令入口与帧处理入口均显式接收连接）；commands 模块新增 4 个命令分支与 2 个解析纯函数；app 模块帧分发新增 6 个 MSG_FILE_* case、公告挂钩、错误挂钩与事件循环轮询集成（发送 tick + 动态 poll 超时）；ui 模块更新帮助文本；协议层新增 3 个组帧函数。术语表 +4 条（文件传输/传输标识/分片/接收目录，已入库）；ADR-0002 记录状态机架构。
- **命令协议契约**（载荷与服务器 file_transfer.c 一致，服务器为唯一权威）：
  - `/sendfile <目标> <文件>` → MSG_FILE_INIT：`target\0filename\0file_size_str`（三段 NUL 结尾字符串，size 为十进制字符串，由本地文件 stat 获得）
  - `/accept <tid>` → MSG_FILE_ACCEPT：`tid(4B 大端)`
  - `/reject <tid>` → MSG_FILE_REJECT：`tid(4B 大端)`
  - `/cancel <tid>` → MSG_FILE_CANCEL：`tid(4B 大端)`
- **S→C 形态**：公告（`[Server] ` 前缀的 MSG_SERVER_MSG）与对应控制帧成对到达、公告先到。接收方收 INIT 帧载荷 `sender\0filename\0size_str`（**无 tid**，tid 只从公告解析）；发送方收 ACCEPT/REJECT/CANCEL 帧（4B tid）；接收方收 CHUNK 帧（`tid+offset+data`）与 COMPLETE 帧；发送方完成确认只靠 complete 公告（帧只发接收方）；断线取消只有 `cancelled: X disconnected.` 文本公告、无帧。公告与帧同为信号，处理幂等（已处理过的状态转移不重复执行）。
- **状态机**：发送 NONE → PENDING_TID（INIT 已发，等自己公告解析 tid）→ PENDING（等 accept）→ ACTIVE（轮询发片）→ WAIT_COMPLETE（等 complete 公告）→ 清理；接收 pending（公告建任务）→ ACTIVE（/accept 落盘收片）→ 完成/取消清理。任一路径收到 reject/cancel 公告或帧、ERR_TRANSFER_STATE(300) → 任务清理（发送关闭文件句柄；接收删除半成品）。
- **单槽规则**：发送全局单槽（槽忙本地拒绝）；接收 ≤8 个 pending + 至多 1 个活动接收（第二个 /accept 本地拒绝；pending 满时对新公告自动回发 REJECT 并提示）。发送与接收槽独立（发送中仍可接收、接收中仍可发送）。
- **轮询分片**：每轮发送 ≤2 片（单片数据 65500 字节，每轮 ≈ 128KB——初始 4 片/轮实测触发服务器写缓冲静默丢包，见 Further Notes 修正记录）；发送期间 poll 超时 200ms → 50ms；**tick 只在 poll 超时轮执行**（事件轮跳过——转发数据连续到达时轮循环会塌缩成忙循环，实测丢包，见 Further Notes）；stdin 先处理保证当轮 /cancel 立即生效不残留；进度每越过 1MiB 打一行。发送失败（conn 发送返回错误）= 连接已断，退出事件循环。
- **落盘安全**：接收文件存客户端运行目录下 downloads/（不存在则创建）；文件名 basename 化（最后 `/` 或 `\` 之后、控制字符替换为 `_`，空/`.`/`..` 拒绝——拒绝时自动回发 REJECT 并提示）；同名加序号（`name`、`name (1)`...）；取消/失败/字节数不符时删除半成品；字节数校验通过才保留（服务器无确认，客户端自行兜底）。
- **纯函数接口**：`commands_parse_sendfile(line, target, target_sz, filename, filename_sz)`——目标取首个空白前 token（≤31）、文件名取剩余行（内部空格保留、≤255，超长拒绝）；`commands_parse_tid_arg(arg, tid_out)`——全数字 + ≤UINT32_MAX，否则 -1。file 模块纯函数：`file_parse_announcement`（公告文本 → 事件类型 + tid）、`file_parse_init_payload`（INIT 帧三段）、`file_basename_sanitize`、`file_unique_name`（exists 探针注入，可测）、`file_join_path`、`file_chunk_count/plan`（分片计划）。
- **协议层**：新增 `protocol_build_text3`（三段 NUL 载荷，镜像服务器 payload_append_field 语义）、`protocol_build_tid`（4B 大端）、`protocol_build_chunk`（tid+offset+data）——客户端超集，protocol.c 与服务器不再逐字节一致（提交说明注明有意偏离）。
- **错误显示**：ERR_TRANSFER_STATE(300)/ERR_NO_SUCH_USER(200)/ERR_NOT_AUTH(1) 均走既有 MSG_ERROR 分支（`错误(码): 消息`），零新增路径；文件相关错误帧到达时若匹配活动任务（如发送中收到 300）则触发任务清理。
- **参数解析规则**：命令后多余空白跳过；/sendfile 缺目标或文件名 → 用法提示；/accept /reject /cancel 参数非数字/超 UINT32_MAX → 用法提示；对不存在 tid 的 /accept /reject /cancel → 本地提示"没有 #N 的传输记录"，不发帧。
- **断连清理**：连接建立与销毁时重置 file 模块（关文件句柄、删接收半成品、清空任务）；发送中连接断开由事件循环退出 + 重置兜底；服务器侧断线自动取消传输并公告对端。
- **发送方本地提示**：/sendfile 提交成功打一行中文确认（服务器公告为英文，中文即时反馈），后续全部依赖公告与进度行。

## Testing Decisions

- **原则**：只测外部行为——解析与决策纯函数的输入→输出映射；不 mock 连接、不 mock 文件系统（唯一化探针注入）、不测实现细节。
- **单元测试**（三个测试缝，先例 `tests/test_commands.c` / `tests/test_protocol.c`，无框架 CHECK 宏）：
  - 命令解析缝：`commands_parse_sendfile`（黄金切分、多空白、文件名含空格、缺目标、缺文件名、目标/文件名超长拒绝）+ `commands_parse_tid_arg`（数字、前导空白、0、空/纯空白、字母、负数、`12abc` 混合、超 UINT32_MAX）→ test_commands 目标
  - 文件域纯函数缝（新目标 test_file）：`file_parse_announcement`（7 种公告文案各一条黄金 + 非文件公告/聊天文本前缀不匹配 → 拒绝 + tid 提取）+ `file_parse_init_payload`（黄金三段/缺段/超长/非数字）+ `file_basename_sanitize`（`a/b/c.txt`、`C:\dir\f.txt`、`.`/`..`/空、控制字符、超长）+ `file_unique_name`（假探针：无冲突/占 1 次/占 3 次/缓冲不足）+ `file_chunk_count/plan`（size=0、整片、余片、index 越界）
  - 协议组帧缝：`protocol_build_text3`（三段 NUL 黄金字节 + 解析往返）、`protocol_build_tid`（黄金字节）、`protocol_build_chunk`（黄金字节、data_len=0 边界、out_cap 不足）→ test_protocol 目标
- **e2e**（`tools/e2e_m4.sh`，比 M3 强的自动断言）：真实服务器 + 多客户端，wait_for 轮询 grep 替代固定 sleep（M3 时序教训）；接收文件与源文件 `diff -q` 校验（字节一致是文件传输的核心验收）；FAIL 计数 + 非零退出码。场景：① happy path（64KB 随机文件，alice→bob，diff 通过）② reject（downloads/ 无残留）③ cancel（8MB 发送中取消，无半成品）④ 目标不在线（错误 200 且槽位释放）⑤ 非法 tid（本地拒绝提示）⑥ 同名加序号（`name (1)` 且 diff 通过）⑦ 多 pending 逐个 accept（两个文件均 diff 通过）。从 `/tmp/e2e_m4/cwd` 运行（downloads/ 不落仓库），日志写 `/tmp/e2e_m4/`。
- **不做**：状态机单测（发送 tick/接收写盘与 I/O 交织，外部行为由 e2e diff 覆盖）；分发逻辑单测（trivial 转发）；服务器行为测试。

## Out of Scope

- 断点续传、chunk 确认与重传（服务器无确认机制，可靠性由客户端按序发送 + 接收校验兜底）
- 多 ACTIVE 并发传输（单槽决策，见 ADR-0002）
- 发送队列（槽忙直接拒绝，不排队）
- 传输目录选择（固定 downloads/）、传输历史记录
- 发送期间源文件被修改的处理（按 fopen 时状态读取）
- 服务器侧超时清理、传输持久化（服务器议题，零改动）
- M5 ncurses TUI

## Further Notes

- **服务器怪癖适配清单**（来自 file_transfer.c 探索，2026-08-10）：tid 只存在于公告文本（INIT 帧无 tid——公告解析失败则无法关联，已知限制）；无 chunk 确认/流控；写缓冲 256KB 超限静默丢包（限流对策）；断线取消只发文本公告（双信号处理）；对已结束 tid 的 CANCEL 静默忽略（不要当错误重试）；断线后 tid 失效（任何帧报 300）；chunk 载荷 <12 字节触发服务器下溢 bug（客户端永不发短 chunk）；file_size 不校验（客户端自己发合法数字）。发送方靠 complete 公告确认完成（COMPLETE 帧只发接收方）。
- **服务器乱序中继（2026-08-10 票 02 冒烟实测）**：服务器线程池并行处理同连接帧，chunk 转发顺序可能与发送顺序不一致（实测 3MB 文件相邻块交换/循环错位：40↔41、45→46→47 循环）。接收方**必须按 offset 定位写盘**（fseek），乱序到达是正常现象；重复/越界 offset 才视为错误。服务器自带测试客户端仅用单 chunk 用例，未覆盖此行为（其盲区）。
- **发满即发 COMPLETE 的竞态（2026-08-10 票 02 冒烟实测，已规避）**：同一 tick 内发完末片后立即发 COMPLETE，服务器线程池下 COMPLETE 可能先于末片 chunk 被处理（状态提前置 FT_COMPLETE），末片被拒丢弃（实测服务器报告 3144000/3145728）。客户端规避：全部片发完后置 FILE_SEND_DONE，**下一轮 tick（≥50ms）才发 COMPLETE 帧**，给服务器 worker 留处理末片的时间。规避后 4 轮冒烟 6 次传输全部字节一致。注意：该竞态若仍发生（极端负载），接收方按字节数校验兜底（删除+提示），发送方只能看到 complete 公告无法感知——已知局限。
- **发送节奏忙循环塌缩（2026-08-10 票 03 实测，已修复）**：原实现 tick 在每轮事件处理之后执行。接收流连续到达时（自环传输实测：转发的 chunk 回给发送方自己），poll 每轮立即返回（不等到 50ms 超时），轮循环塌缩为 ~1ms 忙循环，发送速率失控（strace 实测 4MB 全部 64 片在 47ms 内发出），服务器 worker 转发积压超写缓冲 256KB 上限，静默丢包（4MB 丢 24 片、16MB 丢 122 片，接收方字节数校验兜底删除）。修复（app.c）：**tick 仅在 poll 超时轮（r==0）执行**，事件轮跳过——数据消化完后自然回到超时轮，发送节奏恒定为 2 片/50ms；同时每轮片数 4→2（≈128KB，低于 256KB 上限留余量）。修复后自环/独立双端 16MB、32MB 传输零丢包。
- **INIT 帧关联跨传输交错（2026-08-10 票 03 实测，已修复）**：服务器线程池并行处理不同传输的 INIT，接收方收到的公告/INIT 帧对**可能跨传输交错**（run B 实测：charlie 的 INIT 帧被填入 bob 刚建的 pending 任务，bob 的 8MB 任务被 128KB 的 INIT 载荷覆盖，完成校验误判通过并保存错误文件）。修复（file.c）：接收任务记录公告到达序号（seq），INIT 帧匹配"seq 最小且未填充"的任务——利用"每对公告+INIT 帧相邻入队"的 FIFO 性质（同一 worker 内顺序发送）。
- protocol.c 新增 3 个组帧函数为客户端超集，与服务器 protocol.c 不再逐字节一致——提交说明注明有意偏离。
- 发给自己（/sendfile 自己的用户名）放行：服务器允许 sender==receiver，客户端不做多余限制（协议以服务器为唯一权威）。
- 术语表已同步：CONTEXT.md 新增「文件传输」「传输标识」「分片」「接收目录」四条。
- ADR-0002 记录：轮询分片（有界批量阻塞，ADR-0001 预警的对策）、单槽限并发、公告驱动 tid 解析、落盘安全。
- 已知服务器 bug（2026-08-08 记录，未修）不影响本里程碑：disconnect 广播不唤醒 notify_fd——文件传输断线取消公告可能滞留，e2e 断言不依赖断线公告（用 CANCEL 帧/主动取消场景覆盖取消路径）。
- e2e 日志与工作目录走 WSL `/tmp/`（重启自动清理、不落仓库）；测试账号 alice:password123、bob:password456、charlie:password789。
